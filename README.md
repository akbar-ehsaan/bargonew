# بارگو (نسخهٔ جدید) — چهار پنل مجزا

سامانهٔ اعلام بار و مدیریت حمل‌ونقل با **چهار پنل کاملاً جدا**: راننده، صاحب بار، شرکت حمل‌ونقل و مدیر سامانه.
هر کاربر فقط منوهای نقش خودش را می‌بیند. ساختار کد عیناً از الگوی **رنگیو** پیروی می‌کند: یک پروژهٔ
ASP.NET Core MVC با **Area برای هر نقش**، EF Core و SQL Server.

- **پشته:** ASP.NET Core 10 MVC + EF Core 10 + SQL Server
- **پورت توسعه:** 5810
- **فرانت‌اند:** Razor + CSS خودی، وزیرمتن، bootstrap-icons و Leaflet — همه محلی در `wwwroot`، بدون CDN

## اجرا

```bash
cd src/Bargo.Web
dotnet run
```

پایگاه‌داده (`BargoDb` روی `Server=.`) در اولین اجرا خودکار مهاجرت می‌شود؛ استان‌ها و شهرها، انواع خودرو،
تنظیمات، تعرفه‌ها و حساب مدیر ساخته می‌شوند. در محیط Development دادهٔ نمایشی هم کاشته می‌شود (`Seed:Demo`).

رشتهٔ اتصال را در `appsettings.Secrets.json` (در .gitignore) یا متغیر محیطی `BARGO_ConnectionStrings__Default` بگذارید.

مهاجرت دستی:

```bash
dotnet ef migrations add <Name> -o Data/Migrations
dotnet ef database update
```

   │  └─ Admin/                     پنل مدیر سامانه

   │  ├─ Entities/                  Accounts، Fleet، Freight، Trips، Finance، Support، Platform
   │  └─ ViewModels/

   │  ├─ DriverReadiness.cs         «آیا راننده می‌تواند بار بگیرد؟» (مدارک، انقضا، خودرو)
   │  ├─ WalletService.cs           تنها راه تغییر موجودی کیف پول
   │  ├─ SettingsService.cs         تنظیمات سامانه با پیش‌فرض
   │  ├─ NotificationService.cs، SmsSender.cs، DocumentStorage.cs، AuditService.cs
   │  ├─ ExpiryAlertService.cs      هشدار روزانهٔ انقضای مدارک

پوشهٔ هر Area هم‌نام نقش است (`Areas/Driver`) ولی **فضای نام** آن `Bargo.Web.Areas.DriverPanel.Controllers`
است — مثل `UnionPanel` در رنگیو. بدون این پسوند، نام موجودیت‌ها (`Driver`، `Company`، `Shipper`، `Admin`)
داخل کنترلرها به فضای نامِ Area حل می‌شد و کد کامپایل نمی‌شد. مسیرها از `[Area("Driver")]` می‌آیند و تغییری نمی‌کنند.

کنترلرهای مشترک (تیکت، اعلان، پیام، شکایت) در `Controllers/Shared` هستند و هر Area فقط یک زیرکلاس
چندخطی دارد؛ ویوهایشان در `Views/Shared/Panel`. منوی هر پنل در `Services/PanelMenu.cs` است.

## چرخهٔ اصلی

```
ثبت بار ← انتشار ← مشاهده توسط رانندگان/شرکت‌ها ← پیشنهاد قیمت ← انتخاب پیشنهاد ← ساخت سفر
← تخصیص راننده و خودرو ← بارگیری ← ثبت بارنامه ← شروع سفر ← رهگیری ← تحویل با کد
← تسویه و کمیسیون ← امتیازدهی ← بایگانی
```

### «بار» و «سفر» یکی نیستند

`Load` چیزی است که صاحب بار ثبت می‌کند و پیشنهاد می‌گیرد. با پذیرش یک پیشنهاد از روی آن یک `Trip`
ساخته می‌شود و همهٔ عملیات حمل روی سفر است. لغو راننده یعنی لغو سفر و بازگشت بار به بازار؛ تعویض
راننده/خودرو در `TripAssignments` ثبت می‌شود؛ گزارش و حسابداری بر پایهٔ سفر است.

### قواعدی که نباید دور زده شوند

- **وضعیت‌ها فقط از `TripFlow`** عوض می‌شوند. هر گذار یک `TripEvent` (چه کسی، کی، کجا) می‌سازد که
  «پروندهٔ سفر» مدیر برای رسیدگی به اختلاف از آن ساخته می‌شود.
- **موجودی کیف پول فقط از `WalletService`**؛ هر تغییر یک ردیف با `BalanceAfter` دارد.
- **مالکیت داخل کوئری** (`Scopes.cs`)؛ شناسهٔ حدس‌زده ۴۰۴ می‌گیرد.
- **دروازهٔ تأیید سراسری است**: رانندهٔ/شرکتِ تأییدنشده فقط به صفحه‌های `[AllowUnapproved]` (داشبورد،
  پروفایل، مدارک، تیکت) دسترسی دارد.
- **تحویل فقط با کد یکبارمصرف گیرنده** (تنظیم `Trip.DeliveryOtp`) و **شروع سفر بدون بارنامه ممکن نیست**
  (`Trip.RequireWaybill`).
- مبالغ در پایگاه‌داده **ریال** و در نمایش **تومان**؛ همهٔ تاریخ‌ها **UTC** و در نمایش شمسی به وقت تهران.

## آزمون

دو اسکریپت در `tools/` (پس از `dotnet build`، روی پایگاه‌دادهٔ توسعه با دادهٔ نمایشی). هر دو برنامه را خودشان
اجرا و در پایان متوقف می‌کنند.

```bash
powershell -ExecutionPolicy Bypass -File tools\smoke-test.ps1
powershell -ExecutionPolicy Bypass -File tools\e2e-flow.ps1
```

- **smoke-test.ps1** — با حساب نمایشی هر چهار نقش وارد می‌شود و **همهٔ ردیف‌های منو** (مستقیم از
  `PanelMenu.cs`) به‌علاوهٔ صفحه‌های جزئیات را باز می‌کند؛ هر پاسخی جز ۲۰۰ را با عنوان استثنا گزارش می‌دهد.
- **e2e-flow.ps1** — چرخهٔ کامل را از راه همان فرم‌ها اجرا و هر گام را با خواندن پایگاه‌داده می‌سنجد:
  ثبت بار ← پیشنهاد ← پذیرش و ساخت سفر ← پرداخت از کیف پول ← مراحل سفر ← ردِ شروع بدون بارنامه ←
  ثبت بارنامه ← تحویل (کد نادرست رد، کد درست پذیرفته) ← تسویهٔ خودکار و کمیسیون ← امتیاز.
  هر اجرا یک بار و یک سفر تازه به دادهٔ نمایشی اضافه می‌کند.

> اسکریپت‌ها UTF-8 **با BOM** ذخیره شده‌اند؛ Windows PowerShell 5.1 فایل بدون BOM را ANSI می‌خواند و متن فارسی داخلش را خراب می‌کند.

## پیامک، درگاه و حریم طرفین

- **پیامک واقعی (ICTX):** در «تنظیمات ← پیامک»، `Sms.Provider` را از `log` به `ictx` تغییر دهید و کلید API و
  شماره خط را بدهید (آورده‌شده از پروژهٔ قدیمی بارگو). با `log` هیچ پیامکی نمی‌رود و متن فقط در `SmsLogs` می‌نشیند.
- **درگاه زرین‌پال:** در «تنظیمات ← درگاه پرداخت»، `Gateway.Provider=zarinpal` و شناسهٔ پذیرنده را بدهید؛
  «حالت آزمایشی» به sandbox زرین‌پال می‌رود. شارژ کیف پول از `/Pay/Charge` آغاز و در `/Pay/Callback` با
  Verify قطعی می‌شود (`Services/ZarinPalService.cs` و `Controllers/PayController.cs`). با `demo` شارژ آزمایشی است.
- **هزینه‌های قابل‌تنظیم مدیر:** هزینهٔ بارگیری، تخلیه، صدور بارنامه و «مالیات بر ارزش افزوده» (روشن/خاموش + درصد)
  در «تنظیمات مالی». مثل کمیسیون هنگام ساخت سفر روی آن قفل می‌شوند؛ صاحب بار «کرایه + هزینه‌ها + مالیات» را
  می‌پردازد، بارگیری/تخلیه در تسویه به حمل‌کننده و بارنامه/مالیات به بارگو می‌رسد.
- **مخفی‌ماندن طرفین تا تأیید نهایی:** راننده/شرکت و صاحب بار تا پرداخت کرایه (`Trip.IsPaid`) نام، موبایل و پلاک
  همدیگر را نمی‌بینند (`Services/Privacy.cs`)؛ در مرحلهٔ پیشنهاد همیشه ناشناس‌اند و گفتگو فقط از پیام درون‌برنامه‌ای است.
- **کد تحویل از لحظهٔ ثبت بار:** با انتشار بار، کد تحویل ساخته و به گیرنده پیامک می‌شود (`Load.DeliveryCodeHash`)؛
  «ارسال دوبارهٔ کد» همچنان کد تازهٔ سفر می‌فرستد و جایگزین می‌شود.
- **بیمهٔ بار:** نوع و مبلغ بیمه در فرم ثبت بار گرفته و در صفحهٔ بارنامه نمایش داده می‌شود.

## هنوز نیست

- اپ اندروید و سرویس ردیابی پس‌زمینه (API آماده است: `POST /api/track` با `TrackKey`)
- اتصال به سامانهٔ بارنامهٔ رسمی — بارنامه فعلاً «ثبت شماره» است
